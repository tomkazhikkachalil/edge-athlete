# Messaging: the Message door, the thread on a phone (Oct 14 2026)

> The messaging area's spec, started with Tom's seven fixes of Oct 14 2026 (fix 4 the Message door; fix 6 the thread on a phone). The chat dock (desktop, Jul 28 2026) and the messages pages predate it — read DEVLOG Jul 28–Aug 9 2026 for their history.

## The Message door (fix 4, zero DDL)

Tom: *"Add a Message button on every other user's profile, next to the follow button. Tapping it opens the existing conversation with that user if one exists, or starts a new one. The user lands directly in the chat with the keyboard ready."*

- **One POST is the get-or-create.** `POST /api/messages { type: 'direct', participantId }` finds the direct conversation between the two (even one a side left — it is revived) or creates it, and answers `{ conversationId, existing }`. It is also the ONE place the rules live: blocks (403), a departed account (404), the target's `messaging_permission` (`nobody` / `fans_only` / `mutual_fans`, 403 with the honest sentence), the supervised sender's symmetric rule, the first-contact hold. The profile never asks whether a conversation exists and never repeats a rule.
- **The button** — `src/components/profile/MessageButton.tsx` (`data-profile-message`), the Message half of `ProfileActions`' pair on `/athlete/[id]` and `/u/[username]` (signed in, not yourself; disabled while acting as a managed athlete — a DM is first-person). Tap → the POST → `fetchConversations()` (the list learns a new thread) → `/messages?c=<id>&compose=1`. A refusal shows the API's sentence as the error and leaves you on the profile.
- **`compose=1` means keyboard ready:** `messages/page.tsx` reads it, `ChatWindow` passes `autoFocusComposer`, and `MessageInput` focuses the textarea once the thread has loaded, then the flag is replaced out of the URL (a refresh does not refocus). Android and desktop raise the keyboard at once; iOS raises it only inside a tap, so there the caret lands and one tap opens it.
- **Pinned by:** `e2e/profile-message.spec.ts` (desktop + @mobile at 375 px, both routes): the pair's two buttons share a height and a line; Message lands on `/messages?c=` with the composer focused and the flag consumed; a message sends; the second tap (from `/u/`) opens the SAME conversation (one direct row between the two); `fans_only` without the follow → the API's words in the error and the URL stays on the profile.

## The thread on a phone (fix 6, zero DDL)

Tom: *"Opening a new or existing conversation on a phone behaves badly. The message area collapses toward the top of the screen, the message list stops scrolling and feels frozen, and the text box does not line up with the keyboard."* One cause behind the three: the thread shell sat at the top of the LAYOUT viewport while iOS showed the user a different strip of it (the visual viewport, panned to keep the caret visible); the old `--vvh` + `scrollTo(0,0)` clamp lost that race. Plus three structural facts: the tab bar stayed under the composer on `/messages?c=` (the shell subtracted it, the composer padded the home indicator again — a bar-high gap over the keyboard), the list was `flex-col-reverse` with no scroll rules (WebKit scrolls column-reverse badly), and the textarea was disabled while sending (a blur — the keyboard closed and reopened on every message).

- **The thread owns its bottom edge:** `showsTabBar(pathname, conversationParam)` hides the bar while `/messages` has `?c=` (`TabBar` reads the param under a `Suspense`); the app header is hidden below `lg` while a thread is open (the thread has its own: Back, the name, the menu).
- **The shell FOLLOWS the visual viewport** — `src/components/messages/thread-viewport.ts` (pure, tested): `threadViewportGeometry({ vvHeight, vvOffsetTop, layoutHeight, baselineHeight, bannerH, tabBarH })` → `{ top, height, keyboardOpen, bottomInset }`; the keyboard is detected against the tallest height seen in this orientation (`nextBaselineHeight`, `KEYBOARD_MIN_SHRINK_PX` 120 — an iPad hardware-keyboard bar never counts; Android's `resizes-content` shrinks the layout too, so a layout-minus-visual test would say nothing there); only the part of the sticky banner / fixed bar INSIDE the strip is subtracted. `src/hooks/useThreadViewport.ts` applies it on vv `resize` + `scroll` (one rAF, the pinch guard), writing `--ea-thread-top` / `--ea-thread-h` / `data-keyboard-open` straight onto the shell (`.ea-thread-shell`, `position: fixed; top:` — never a transform; inert from `lg`), locks the body, and pads the safe areas: the bottom one leaves with the keyboard open. `useFollowVisualViewport` is the raw half for the GIF sheet.
- **The list is a plain column and `useThreadScroll` is the ONE writer of its scrollTop** — `list-scroll.ts` (pure, tested): the first load lands at the bottom; your own message or one arriving while you are within 80 px of the bottom scrolls to it; one arriving while you read history shows the "New message" pill (`data-new-messages-pill`); older messages prepended keep what you were reading in place (`restoreAfterPrepend`); the list sticks to the bottom as it or its content changes size while you are there (the keyboard, the composer growing, an image loading); the keyboard opening goes to the latest message. `messages` stays newest-first in state (the realtime merge, the older-page append and the send prepend untouched); reply / quote jumps scroll the LIST, never the window. The dock's `MiniChatWindow` keeps its own list.
- **The composer never blurs on a send:** the field is not disabled while sending (the Send button carries it), the text clears at once and comes back on an error, the Send tap does not move focus (`onPointerDown` preventDefault). The field grows 40–120 px and scrolls inside itself (unchanged). The GIF button blurs the field first (the sheet wants the whole strip); `GifPickerModal` sits inside the visible strip (its own search box raises the keyboard) and does not refocus the composer on close. The emoji panel and the attach popover are anchored to the composer, which now follows the keyboard.
- **Pinned by:** `thread-viewport.test.ts`, `list-scroll.test.ts`, the extended `tab-bar.test.ts`; `e2e/messages-mobile.spec.ts` (@mobile, 60 seeded messages): no tab bar while a thread is open, the shell is the viewport and the composer on its bottom edge, the list scrolls and opens at the latest, older messages keep your place, a send keeps focus, the pill for a history reader, the GIF sheet leaves the layout where it was, a shorter viewport (the keyboard's stand-in) keeps the composer on the edge and the latest in view, the field's 120 px cap. **What only a phone proves** (Tom's pass: iOS Safari, Android Chrome, the installed app, portrait and landscape): the composer touching the keyboard with no gap and no flicker on a send; no collapse to the top; finger scrolling with the keyboard up; the standalone insets; Android's keyboard detection; GIF search with the keyboard up; pinch-zoom leaving the layout alone.
