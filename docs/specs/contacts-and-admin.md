# Contacts and the admin console

> The flow changes program, Oct 19 2026 (items 1 and 2 of Tom's list). Convention 47 is the contact list; Convention 48 the admin console's own door. Read the devlog entries of Oct 19 2026 (Flow changes A1–A3, B1–B3) before changing any of it.

## Convention 47 — A sign-up or inquiry is a contact row, a mail to ONE setting, and a confirmation the person reads (migration 266, #1231–#1233)

Tom: *"When someone signs up for notifications or sends an inquiry, nothing happens with it right now."*

- **The row.** `contacts` (266) holds one row per submission — `email` (lowercased), `name`, `source` (`notify_signup | inquiry`), `message`, `marketing_consent`, `consent_text` (the exact words the checkbox showed — CASL wants express consent, recorded), `user_type`, `created_at`. RLS on, NO policies: service-role only (the 027 posture; these are addresses of people who are not users). The list keeps history; the export dedupes. The 027 `waitlist` rows were copied in with consent false; `waitlist` is history, never written again.
- **ONE writer:** `src/lib/contacts/contacts-server.ts recordContact` — the row, then a best-effort mail. A repeat from the same address and source inside 24 h (`REPEAT_MAIL_WINDOW_MS`) is a row but no second mail. A failed mail is Sentry's, never the visitor's: the request still answers 201.
- **ONE door:** `POST /api/contacts` — public (the coming-soon page is signed out); the guest ticket's posture: a `website` honeypot (a bot's "success", nothing stored), the `contacts` IP bucket (5 / h), bounded text, an inquiry needs a message. Pre-266 a 503 by name. `/api/waitlist` is gone (A2).
- **ONE setting:** the mail goes to `app_settings.notify_inbox_email` (266; edited on the console's inbox card through `PUT /api/admin/settings`, a key from `APP_SETTING_KEYS` only) — then `CONTACT_EMAIL`, then `EMAIL_FROM`. Never a hardcoded address. `notifyInboxAddress` caches a minute; the write clears it. SMTP unset = the row is kept and the mail skipped. "Send a test email" (`POST /api/admin/contacts/test-mail`) answers honestly (`smtp_unset` · `no_address` · `provider_refused`), never a 500 for a mail that did not go.
- **The mail:** `emailService.sendContactNotification` through `deliver()`, Reply-To the visitor, subject "New sign-up: {name or email}" / "New inquiry: …", a plain-text body of the five facts (name, email, date, source, consent) and the message.
- **The forms** (A2): the coming-soon page (`ComingSoon.tsx`) — Notify me takes an optional name and an UNTICKED consent box; "Have a question? Send us a note" turns it into an inquiry with a required message; the confirmation replaces the form (`role="status"`, names the person and the address) and the sign-in door stays under it. The landing popup (`WaitlistPopup`) takes the same fields. The consent sentence is ONE string — `COPY.CONTACTS.CONSENT_LABEL` ≡ `MARKETING_CONSENT_TEXT`, pinned by test — and travels with the row as `consent_text`.
- **The console** (A3): `/admin/contacts` (`/dashboard/contacts` until B2) — the inbox card, then the list (`ContactsPanel`: source / consent / search filters, 50 a page, a tap opens the message) and two downloads from `GET /api/admin/contacts/export`: `?list=all` (every submission) and `?list=marketing` (the consented addresses, one per email — `marketingList`: the LATEST submission that showed the checkbox decides). The CSV is RFC 4180 and **formula-safe** (`csvEscape` prefixes `= + - @` tab CR with `'`). Past 10,000 rows the file's last line says it is a floor. A Contacts tile with the counts sits beside the Support queue tile.
- **Pinned by:** `src/lib/__tests__/contacts.test.ts` (the CSV, the dedupe and consent rules, the repeat window, the subject and body, the migration's sources and RLS, the consent sentence), `e2e/contacts-api.spec.ts`, `e2e/coming-soon.spec.ts`, `e2e/admin-contacts.spec.ts` (admin-positive; skips without `E2E_ADMIN_EMAIL`).

## Convention 48 — The admin console is its own door: its own sign-in, its own cookie, the app session never grants it (#1234–#1236, zero DDL)

Tom (Oct 19 2026): *"Take the admin dashboard out of my profile and make it a separate web page. It stays part of Edge Athlete but has its own admin login and password."* His choice among three shapes: a separate sign-in with admin accounts.

- **The door:** `/admin/login` takes the email and password of an account that is an admin by today's sources — `ADMIN_EMAILS` (owner) or a `platform_admins` row (moderator) — checks them against Supabase Auth with a THROWAWAY client (the session it returns is discarded; it is never written as an app cookie) and sets **`ea_admin`**: HttpOnly · `SameSite=Strict` · `Path=/` · 12 h, a jose HS256 token on the server-only **`ADMIN_SESSION_SECRET`** (≥ 32 chars). Unset secret = the door is off: the login answers 503 by name and says so on the page. One refusal sentence whatever was wrong; two buckets (`admin-login-ip` 20 / 15 min, `admin-login` 5 / 15 min per IP + email). `?next=` is honoured only inside `/admin` (`safeAdminNext`). `POST` / `GET` / `DELETE /api/admin/session` are the three verbs; `GET` carries the actor's `id`.
- **The gates:** `requireAdmin` and `requireModerator` read the console cookie FIRST. An owner's cookie is the owner (re-checked against the allowlist); a moderator's is re-checked against `platform_admins` on every request (removal bites at once). A cookie that is present but not enough — a moderator on an owner route, a revoked role — is **refused by name (403), never handed to the app session**. B1 and B2 let the app session pass when there was no cookie; **B3 flipped them to cookie-only** (#1236): no cookie → 401 `Admin sign-in required`; the app session never grants admin, and `/api/admin/me` answers only from the cookie (the app header shows its admin entries only to a browser that also holds it).
- **The pages:** a third root layout, `src/app/(admin)/` (fonts, globals, the nonce'd theme script, the icon sheet, `noindex`; no app providers, no tab bar). `/admin/login` outside the console group; everything else under `src/app/(admin)/admin/(console)/` whose server layout reads the cookie (no cookie → the login, no flash) and whose client `AdminSessionProvider` probes the session ONCE for every page's `useAdminAuth()` — the same `{ user, loading }` shape the app's `useAuth()` has, so the moved pages kept their effects. `AdminHeader` (who is signed in, Sign out, Open the app) replaces `AppHeader`. **Every `/dashboard/*` path redirects to `/admin/*`** (`src/app/(app)/dashboard/[[...rest]]/page.tsx`) — bookmarks, the bell's ticket links (`tickets/server.ts`), the listing notifications, the snapshot's recovery links all land. The launch gate lets `/admin` through (its own sign-in protects it); `admin` is a reserved org-site slug.
- **The specs:** a spec that acts as an owner or a moderator signs in HERE — `e2e/helpers/admin.ts adminSignIn(ctx | api, user)` after the user exists and holds its role (a QA user carries its password; the shared four do in `e2e/.auth/user*.json`). Owner-positive specs still need `E2E_ADMIN_EMAIL` in the build's `ADMIN_EMAILS` AND `ADMIN_SESSION_SECRET` on the target; they skip with the reason otherwise.
- **Pinned by:** `admin-session.test.ts` (mint / read, expiry, tamper, a forged payload, the TTL ceiling, the secret length, the next guard, the gates' order), `launch-gate.test.ts`, `e2e/admin-login.spec.ts`, and every admin spec through the helper.
