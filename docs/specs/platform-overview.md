# The platform Overview: the console's numbers, built to hold at a billion accounts

> The flow changes program, item 2b (Oct 19 2026, PRs H0–H4: #1237 … ). Read the devlog entries "Flow changes H0 … H4" before changing any of it. The admin console itself is Convention 48 (`contacts-and-admin.md`).

## Convention 49 — Every number on the Overview is read from a SMALL table: counted once a night over an index, estimated where exact would be a scan, sampled where it is a probe

Tom: *"we need the ability to see all the stats about the app — health, users, new users, posts … think of what would be useful if we reach a billion people."* His decisions: record one activity mark per account per day; nightly rollups plus "today so far" plus live health, never counts on page load; the `/admin` home is the Overview.

- **The page never counts a big table.** `GET /api/admin/overview?range=7|30|90` reads `platform_stats_daily` (≤ range × metrics rows, plus the window before for the deltas), ≤ 14 days of `platform_health_samples`, `platform_jobs`, two catalog RPCs and today's cached partial run. Nothing else. The model is pure (`src/lib/platform-stats/overview.ts`): a day is 0 when it was rolled up and has no row, **null before the first rollup** (no false cliff); deltas compare this window with the one before; totals are `pg_class` estimates shown with "≈" and their `last_analyze`.
- **The rollup** (`platform_rollup_day(day, group, partial)`, 267; `src/lib/platform-stats/rollup-server.ts`): one UTC day, one GROUP at a time (users · cohorts · content · community · totals · site · storage), each count an index range over that day's rows (O(the day)), an index count on `profile_seen` (O(active accounts)) or an estimate (O(1)); a final run DELETES the day's rows for the group's metrics and INSERTS (never an upsert — a recompute leaves no stale dim); a partial run writes nothing. The registry `PLATFORM_METRICS` (`metrics.ts`) is pinned against the function body by test: a metric joins it only with the index its query needs (the 267 twin added `created_at` on activities, workout_sessions, tickets, organizations). **The nightly job** is `POST /api/cron/platform-rollup` (202 + `waitUntil`, a 240 s budget, scheduled by pg_cron at 00:10 UTC on production — 268); the daily cron's last phase re-asserts T−1 and T−2 inside 15 s (staging's only rollup); `POST /api/admin/platform-stats/recompute?day=` is the owner's door and the backfill. A group that fails or runs out of budget is named; the others still land; the job records itself (`platform_jobs.duration_ms` is the number that says when to move the hour or split the job).
- **Active means "opened the app signed in".** `profile_seen` (267) is ONE row per account — `first_day` is the SIGNUP day (an `AFTER INSERT` trigger on profiles plus a seed), `last_day`, a 63-day `days_mask` bitmap — bumped once per account per UTC day by `bump_profile_seen` in ONE idempotent statement (the int8 shift is capped: Postgres masks `1 << 64` to 1). The mark is sent by the app-shell beacon (`SeenBeacon` → `POST /api/seen`, the device remembers the day, a cookie dedups tabs, 204 whatever happens) — the app-shell, not the middleware (service-worker documents and client navigations never pass it; a token-in-header RPC would need an EXECUTE grant to `authenticated`). It is the account's own activity, not cross-user measurement, so it is not gated on Do Not Track; nothing about WHAT was done is kept; the row dies with the account (`ON DELETE CASCADE`); service role only; never shown per person. DAU / WAU / MAU are index counts on `last_day`; **retention is strict-day Dn** — of the accounts whose `first_day` is C, how many were seen ON day C+n — exact from the bitmap, keyed by the cohort day.
- **Health is sampled, never polled.** `/api/cron/health-sample` (every 5 minutes on production, 268) does ONE index HEAD — `probeDatabase`, shared with the public `/api/health`, never called over HTTP — and writes one row; the page shows now / p50 / p95 and **uptime = ok samples ÷ EXPECTED slots: a missing slot is DOWN** (the sampler cannot write "down" while the app is down); `sampler: 'absent'` after 30 quiet minutes (staging). Days are UTC everywhere.
- **Errors** are Sentry's `stats_v2` through a READ-ONLY `SENTRY_STATS_TOKEN` (never the build token): the nightly rewrites the last 14 days (`errors.sentry` — the counts settle late), the page's last 24 h is cached 5 minutes and a refusal keeps the last value marked stale; unset → "Connect Sentry", no request made. **Storage** is the nightly's last group (a per-bucket sum — a full scan of `storage.objects`, nightly only). **Jobs:** every cron records its last run through `recordJobRun` / `recordJobSummary`; `platform_cron_runs()` adds pg_cron's own rows.
- **What breaks first past tens of millions a day, and the escape** (also in `docs/HARDENING.md`): `users.dau` ≈ 1–3 min at 10⁸ actives (fine in the 300 s job, fatal in `daily` — hence the split); WAU/MAU at 3×10⁸ → a **sampled partial index** (`WHERE (hashtext(profile_id::text) & 127) = 0`, count × 128), not partitioning (an UPDATE moving `last_day` across partitions makes every write heavier) and not a warehouse yet; `posts.new` past ~10⁷ rows a day → a write-time counter; storage past ~10⁷ objects → a per-bucket tally fed by the app's own uploaders; the bump itself is one non-HOT update per active account per day (per-table autovacuum knobs on `profile_seen`; watch `n_dead_tup`).
- **The charts** are plain SVG: one axis; a lone series a 2 px brand line; several thin stacked bars in a FIXED categorical order (the dataviz skill's reference slots 1–4, validated against the app's light and dark surfaces; light flags aqua and yellow under 3:1 — the table view and the tooltip's labels are the relief); recessive grid; nearest-column crosshair with an HTML tooltip; HTML date labels; a legend only for ≥ 2 series; a Table toggle on every chart; dark steps chosen, not flipped. Text wears the text tokens; only marks carry a hue.
