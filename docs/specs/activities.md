## Convention 30 — Activities are not sports: one normalized shape, parsed where it must be, the route private at both ends (Activities program, Sep 29 2026, #1003–#1008, mig 245 the ONLY DDL)

**Activities are not sports: one normalized shape, parsed where it must be, the route private at both ends (Activities program, Sep 29 2026, #1003–#1008, mig 245 the ONLY DDL)** — Tom: athletes bring what their watch or app recorded; phase 1 is FILE import (.FIT / .GPX / .TCX), providers (Strava, Google Health, Garmin) are later adapters onto the same `NormalizedActivity` (`src/lib/activities/types.ts`). `activities` (posture A) is one row per activity; `activity_type` is its OWN list (`catalog.ts` ≡ 245's CHECK), never a `SportRegistry` key, and phase 1 writes no `athlete_performances`. The dedupe key is the START SECOND (`fileExternalId`) — the same run as .FIT and .GPX is one activity. GPX/TCX parse in the BROWSER (Vercel's 4.5 MB cap; regex scanner, no DOMParser) into `wire.ts`; a .FIT uploads RAW to `/api/activities/fit` — **`@garmin/fitsdk` is SERVER-ONLY (its license: Garmin confidential, not to be made available to third parties; a test holds every import to a `-server` module)**. `write-server.ts importActivity` is the ONE writer (server-computed totals, a device total kept only when plausible, stream to storage BEFORE the row). `read-server.ts resolveActivityAccess` is the ONE gate (self / guardian → owner; departed, blocked, Only me → 404; `canViewProfile` or public signed-out) and `visibility.ts` the projection: a viewer's route is trimmed 200 m at BOTH ends (`trimStream`; `route_preview` is stored trimmed), a SUPERVISED athlete's viewers get no position at all (Tom's rules); every response `private, no-store`. Streams are gzipped JSON at `uploads/activities/<profile>/<id>.json.gz` — a PROTECTED prefix, removed by the delete and the deletion engine (`goes`). Share to feed: the posts route REBUILDS `stats_data {type:'activity'}` from the row (a client's is a request). **Activities are a section of VITALS since Oct 1 2026** (they were their own tab): `src/lib/vitals/session-math.ts` is the one week rule over workouts AND activities (`VitalsSession`; the workout-only helpers delegate), `?tab=activities` opens Vitals at that section on BOTH profile routes, the Vitals "Workouts" privacy aspect hides the listing from a viewer, and a shared activity is a `training` post. **Connected apps (Oct 1 2026, mig 247 — PAUSED and hidden in PRODUCTION since Oct 2 2026, Tom: watch connections return with the native apps, `docs/ROADMAP_2026-10.md`; the flag stays on in CI, Preview and locally so the code keeps its tests):** a watch or app is connected ONCE in Settings → Connected apps (`NEXT_PUBLIC_FEATURE_CONNECTED_APPS`, a surface flag) and delivers by itself — `activity_connections` (posture A, `goes`; ONE reader / writer `activities/connections-server.ts`, no response ever carries `secret_ciphertext` or `token_hash`), provider tokens sealed by `crypto/secret-box-server.ts` (`CONNECTIONS_ENC_KEY`, fail closed), `ACTIVITY_SOURCES` / `CONNECTION_PROVIDERS` ≡ 247's CHECKs with each provider's honest `stage` (Strava left out by decision — its terms forbid showing an activity to anyone else), ONE activity however many deliveries (`dedupe.ts`: a start within 60 s and a duration within 10% is the same activity, replaced only by a richer copy), a supervised athlete cannot connect. The Apple Watch path is the personal upload link (`POST /api/activities/inbound/[token]` — no session, the token is the authorization, sha256 at rest, shown once; `adapters/health-export.ts` is pure and never guesses). Polar is OAuth (`providers/polar*.ts`): a SIGNED state binds the callback to the session that started it, the webhook's signature is its gate (the payload's `url` is never fetched), a 401 from Polar marks the connection revoked, the terms' credit is `sourceCredit` ("Recorded with Polar", words not a logo) and the consent line is shown before the athlete leaves; a provider is offered only when the deployment holds its credentials AND the sealing key. The feed card is a line drawing (`route-svg.ts`, no Leaflet in the feed), Create → Activity. **The activity page's map is a FRAMED picture, never a free map (Oct 9 2026, `src/lib/activities/route-frame.ts`):** the box is computed on the client from the stream THIS viewer was given (never stored — a stored box would leak the trimmed ends), padded 25 % with a 400 m minimum span; Leaflet gets `maxBounds` + `maxBoundsViscosity: 1`, `minZoom` = the padded box filling the container (recomputed on resize), `maxZoom` 17, no zoom control (a "Fit route" pill), no scroll-wheel / box / keyboard zoom, the attribution kept, the OSM layer muted (`ea-route-frame`), reduced motion honoured; `data-map-*` on the container are the e2e hooks. Under Save-Data (`src/lib/net/reduced-data.ts`; the public site's live island keeps its own two-line reader because guardrail B4.11 pins its imports — the two are pinned equal by test) the page shows the line drawing with "Show map". `docs/ACTIVITIES.md` is the reference (the provider seam, Strava's owner-only rule); read DEVLOG Sep 29 2026 (Activities PR 1–6) first.
**Live Activities (Oct 4 2026, #1068–#1076, migs 250 · 251 — `docs/ACTIVITIES.md` "Recording live"):** a walk, run, ride, swim, row or any of 26 timed types (three groups, `recording: gps | timer | duration`) is recorded LIVE at `/activities/record` into THIS pipeline as `source 'live'` — never a workout kind. The screen owns no rule: `record/recording.ts` is the pure state machine (fixes admitted ≤ 50 m / ≤ 1.5 × maxSpeed, none while paused — a pause IS a gap; elapsed from clock deltas), `record/storage.ts` the IndexedDB draft (resume after a reload), the import door the recorder's door (`format: 'live'`, `external_id live:<recordingId>` — a retry never duplicates; segments re-clamped and STEPS ESTIMATED on the server, "est." — the web has no pedometer; a watch twin keeps the richer stream and the recorder's segments). A web page gets GPS only in the foreground with the screen on (wake lock; a hidden page is a gap the return toast names) — `ROADMAP_2026-10.md` §2's "not a recorder" is superseded. **Segments are boundaries, measured from the stream at read time** (`segmentStats`, never stored), reach every audience WHOLE (a time range reveals no place). **Photos** (`activity_media`, 216's shape): the owner's file only (`posts/<profile>/`), `at_s` → the pin is DERIVED from the VIEWER's trimmed stream (none inside the 200 m, none for a supervised athlete's viewers), mirrored into the post on share. **An activity is not a sport until the athlete POSTS it as one** (the share-time bridge, `sport-bridge.ts`): swim → swimming, ride → cycling, run → running, row → rowing — four `StatLinePostAdapter` sports on ONE endurance stat line (`enduranceSchema`; km for land, m for water; pace lower-is-better); the posts route builds the line from the ROW and `fromStatLinePost` writes the performance row. The gym path: the workout catalog has walk / hike / elliptical and `workoutToSession` carries `distanceM`. **GPS quality (Oct 9 2026, `src/lib/activities/gps-filter.ts`):** the recording keeps every RAW fix with its accuracy (`acc`; only stale and > 50 m are refused at the door); ONE pure, deterministic fold — `liveRoute` = refusals (the type's accuracy limit, stale, a jump measured against the FILTERED position) → a cold-start settle (3 fixes within 20 m, the route starts at their MEAN) → a constant-velocity Kalman filter per axis (measurement noise = accuracy², a manoeuvre boost) → emission only when confidently moving and > 6 SD from the last drawn point (between steps nothing; standing still repeats the last point — 0 m added) → a 5-sample elevation median — runs on the phone (the map, `liveTotals`, "Finding GPS…") AND in the writer for `source 'live'` (watch / file imports untouched), so the saved distance is the one on screen. The raw fixes are stored in the stream's `raw` block for re-processing and are SERVER-ONLY (`projectStream` strips them for every audience). Locked-phone recording is impossible for a web page — it is the native-app round. Read DEVLOG Oct 4 2026 (Live Activities PR 0–8) and Oct 9 2026 (GPS accuracy) first.
