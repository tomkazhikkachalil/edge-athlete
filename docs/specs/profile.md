# The profile: sports, photos, Training (profile quick fixes, Oct 14 2026)

> The profile's own spec. Tom's five quick fixes of Oct 14 2026 (PRs #1184 … ) and the rules they left behind. His standing rule for the program: nothing gets broken — every PR proven on staging on every project, at 375 px on BOTH profile routes, and on production before the next starts.

## Sports on the profile (PR 3, migration 263 — the program's first DDL)

Tom: *"This app is for all sports, and the profile should reflect what each user actually plays."* Every sport the person has shows; golf gets no special treatment; the user PINS the sports they want most visible (pinned first and larger, the rest in a compact list); the section auto-fills from onboarding; a sport is added by playing it or choosing it in settings; no sport → an empty section with a prompt (no golf fallback — Tom's resolution); other people's profiles show the same list in the same order with no controls.

- **The data:** `sport_settings` (076) carries `pinned` and `pin_order` (263: `CHECK` ties the two, a partial `UNIQUE (profile_id, pin_order) WHERE pinned`). `profiles.sport` stays the declared PRIMARY (the head, the feed sidebar, `?edit=sport`); it is NOT an implicit pin — pins are explicit, the primary merely leads the compact list.
- **The ONE order:** `src/lib/sports/profile-sports-order.ts orderProfileSports` (pure, zero imports) — pinned by pin order (registry order breaks ties), then the primary, then registry order; a pin on a sport that is not active is ignored. The reader applies it, so the strip, the Stats chips and the CDN-cached `/u/` payload agree.
- **The reader never drops a sport:** `assembleSkillCard` always returns a card (`state: 'empty'` → "No stats yet"); `SportSkillCard` carries `enabled`, `state`, `pinned`, `pinOrder`. A declared or settings-row sport counts whatever its `enabled` flag (tennis shows; its stats door is "Stats coming soon"); a sport known ONLY from posts keeps the old rule (renders only with data — a draft or hidden post never surfaces a sport to a stranger).
- **Playing it adds it:** `src/lib/sports/declare-server.ts declareSport` is the ONE writer of a sport's empty row — called from `POST /api/posts` after a PUBLISHED non-general post, and by the pins writer. Idempotent, never throws, never fails the user's write.
- **The pin write:** `PATCH /api/sport-settings { sport, pinned, position? }` (owner only; NOT on THE write-gate list — presentation of one's own profile, like `vitals-privacy`); the rule `src/lib/sports/sport-pins.ts applyPinChange` (`MAX_PINNED_SPORTS` 4, the whole packed list every time, `pin_cap` refused by name); the writer `pins-server.ts writeSportPins` (declare, unpin all, write 1..n). The route answers `{ pins, skillCards }`.
- **The UI:** `src/components/profile/ProfileSports.tsx` on all three routes (`#sports` kept, the `"{Sport} stats"` button names kept): pinned = large cards, 1-up at 375 px / 2-up from `sm`; the rest = the compact rows; the owner's Pin / Unpin and Move up / down are SIBLINGS of the stats button; the owner's empty state "No sports yet — Add sports" opens Edit Profile's Basic tab; a viewer gets no controls and nothing when empty. `SportMultiSelect` offers every registry sport (a disabled one selectable, badged "Coming soon"); `MAX_SELECTED_SPORTS` governs ADDS in the picker — played sports arrive by playing.
- **Caches:** the owner's own `/athlete` skill-cards fetch is `no-store`; `/skill-cards` keeps `private, max-age=60`; `/u/` stays CDN 60 s.
- **Pinned by:** `profile-sports-order.test.ts`, `sport-pins.test.ts`, the updated `skill-cards.test.ts` / `active-sports.test.ts`, and `e2e/profile-sports.spec.ts` (@mobile, both routes).

## Profile photos (PR 4 — part A, zero DDL; part B — the kept original and Adjust — is PR 5, migration 264)

Tom: *"Once a user has set a profile picture and a background photo, the upload icons disappear … Tapping the profile picture or the background opens it larger, with an Edit button … Take a new photo / Upload a new photo / Remove the photo … a live preview of the crop in the shape it will appear."*

- **Two slots, one engine:** `src/components/profile/ProfilePhotoUploader.tsx` is parameterised by `slot` (`PHOTO_SLOTS`: `avatar` round 1:1 at 512 px, 5 MB, `POST /api/upload/avatar`; `cover` 3:1 at 1500 px, 10 MB, `POST /api/upload/cover`). Two native inputs (a library pick; a `capture` input — front camera for the picture, rear for the cover; never `getUserMedia`), the crop-only editor (`EditorConfig.tools: ['crop']` — the tab row disappears for one tool; `CropStage` previews the final shape), then either `immediate` (POST, `onUploaded`) or `deferred` (`onFileReady` — Edit Profile holds the file and uploads on Save). `AvatarUploader` and `CoverPhotoUploader` no longer exist.
- **One door:** `ProfilePhotoDoor.tsx` (`role="dialog"`, `data-photo-door={slot}`, z-[70] above the viewer): Take a new photo · Upload a new photo · Remove the photo (only with a photo; the house `ConfirmModal` at `overlayZClass="z-[80]"` naming what is lost). A guardian passes `targetProfileId` (both routes' acting gate).
- **Tap to view:** `ProfileCoverHeader` takes `onCoverTap` / `onAvatarTap` — passed ONLY when a photo is set, on all three routes; `ProfilePhotoViewer.tsx` is the house `MediaLightbox` with one item (the counter shows only for >1) and a `topAction` Edit for the owner that opens the door. **The pulled-up avatar row is `pointer-events-none`** (only the avatar wrapper takes the pointer): it overlaps the cover's lower band and used to catch every tap there — the cover's view button and the owner's Add cover photo control. Never give that row a pointer again.
- **Buttons only while a slot is empty:** `/athlete` renders "Add profile picture" / "Add cover photo" (`data-add-avatar` / `data-add-cover`) only when the column is null; once set, the photo itself is the door (tap → viewer → Edit). Edit Profile's Basic tab offers BOTH photos (Change profile picture / Change cover photo, with a preview of the pending pick); `basicForm.cover_file` rides beside `avatar_file`.
- **Remove:** `DELETE /api/upload/avatar` and `DELETE /api/upload/cover` (the POSTs' files, so THE write-gate list is unchanged) null the column and remove OUR file only — `src/lib/profiles/photo-paths.ts managedProfilePhotoPath(url, slot)` (pure: the four legacy avatar buckets, `covers/`; a Google or foreign URL → null); the avatar's `/u/` head revalidates. `PUT /api/profile` strips `cover_url` as it does `avatar_url`.
- **Pinned by:** `photo-paths.test.ts`; `e2e/profile-photos.spec.ts` (@mobile — Chromium, WebKit and Android): empty → both buttons; each added through the door → the buttons go; tap → viewer (no counter) → Edit → Remove → confirm → the button and the file; Edit Profile offers both photos.
