# The profile: sports, photos, Training (profile quick fixes, Oct 14 2026)

> The profile's own spec. Tom's five quick fixes of Oct 14 2026 (PRs #1184 … ) and the rules they left behind. His standing rule for the program: nothing gets broken — every PR proven on staging on every project, at 375 px on BOTH profile routes, and on production before the next starts.

## Sports on the profile (PR 3, migration 263 — the program's first DDL)

Tom: *"This app is for all sports, and the profile should reflect what each user actually plays."* Every sport the person has shows; golf gets no special treatment; the user PINS the sports they want most visible (pinned first and larger, the rest in a compact list); the section auto-fills from onboarding; a sport is added by playing it or choosing it in settings; no sport → an empty section with a prompt (no golf fallback — Tom's resolution); other people's profiles show the same list in the same order with no controls.

- **The data:** `sport_settings` (076) carries `pinned` and `pin_order` (263: `CHECK` ties the two, a partial `UNIQUE (profile_id, pin_order) WHERE pinned`). `profiles.sport` stays the declared PRIMARY (the head, the feed sidebar, `?edit=sport`); it is NOT an implicit pin — pins are explicit, the primary merely leads the compact list.
- **The ONE order:** `src/lib/sports/profile-sports-order.ts orderProfileSports` (pure, zero imports) — pinned by pin order (registry order breaks ties), then the primary, then registry order; a pin on a sport that is not active is ignored. The reader applies it, so the strip, the Stats chips and the CDN-cached `/u/` payload agree.
- **The reader never drops a sport:** `assembleSkillCard` always returns a card (`state: 'empty'` → "No stats yet"); `SportSkillCard` carries `enabled`, `state`, `pinned`, `pinOrder`. A declared or settings-row sport counts whatever its `enabled` flag (tennis shows; its stats door is "Stats coming soon"); a sport known ONLY from posts keeps the old rule (renders only with data — a draft or hidden post never surfaces a sport to a stranger).
- **Playing it adds it:** `src/lib/sports/declare-server.ts declareSport` is the ONE writer of a sport's empty row — called from `POST /api/posts` after a PUBLISHED non-general post, and by the pins writer. Idempotent, never throws, never fails the user's write.
- **The pin write:** `PATCH /api/sport-settings { sport, pinned, position? }` (owner only; NOT on THE write-gate list — presentation of one's own profile, like `vitals-privacy`); the rule `src/lib/sports/sport-pins.ts applyPinChange` (`MAX_PINNED_SPORTS` 4, the whole packed list every time, `pin_cap` refused by name); the writer `pins-server.ts writeSportPins` (declare, unpin all, write 1..n). The route answers `{ pins, skillCards }`.
- **The UI:** `src/components/profile/ProfileSports.tsx` on all three routes (`#sports` kept, the `"{Sport} stats"` button names kept): pinned = large cards, 1-up at 375 px / 2-up from `sm`; the rest = the compact rows; the owner's Pin / Unpin and Move up / down are SIBLINGS of the stats button (they stay — Tom, Oct 25 2026: arranging one's own view, not editing); **no sport → nothing, for the owner as for a viewer** (Convention 52 — the owner's empty state "No sports yet — Add sports" was removed Oct 25 2026; Edit Profile's Sports tab, reached by the pencil, the header menu or `?edit=sport`, is where sports are added); a viewer gets no controls. `SportMultiSelect` offers every registry sport (a disabled one selectable, badged "Coming soon"); `MAX_SELECTED_SPORTS` governs ADDS in the picker — played sports arrive by playing.
- **Caches:** the owner's own `/athlete` skill-cards fetch is `no-store`; `/skill-cards` keeps `private, max-age=60`; `/u/` stays CDN 60 s.
- **Pinned by:** `profile-sports-order.test.ts`, `sport-pins.test.ts`, the updated `skill-cards.test.ts` / `active-sports.test.ts`, and `e2e/profile-sports.spec.ts` (@mobile, both routes).

## Profile photos (PR 4 — part A, zero DDL; part B — the kept original and Adjust — is PR 5, migration 264)

Tom: *"Once a user has set a profile picture and a background photo, the upload icons disappear … Tapping the profile picture or the background opens it larger, with an Edit button … Take a new photo / Upload a new photo / Remove the photo … a live preview of the crop in the shape it will appear."*

- **Two slots, one engine:** `src/components/profile/ProfilePhotoUploader.tsx` is parameterised by `slot` (`PHOTO_SLOTS`: `avatar` round 1:1 at 1024 px (512 until Oct 15 2026), 5 MB, `POST /api/upload/avatar`; `cover` 3:1 at 1500 px, 10 MB, `POST /api/upload/cover`). Two native inputs (a library pick; a `capture` input — front camera for the picture, rear for the cover; never `getUserMedia`), the FULL post editor (Oct 15 2026 — Tom: "the same editing toolsets as a post"; it was `tools: ['crop']`): Crop · Adjust · Filters · Masks · Retouch · Text · Perspective, the slot's ratio enforced (`CropStage` on the Crop tab; on every other tab a round frame `[data-circular-preview]` over the engine preview for the picture, so text or a mask near a corner looks clipped while placed), then either `immediate` (POST, `onUploaded`) or `deferred` (`onFileReady` — Edit Profile holds the file and uploads on Save). `AvatarUploader` and `CoverPhotoUploader` no longer exist.
- **One door:** `ProfilePhotoDoor.tsx` (`role="dialog"`, `data-photo-door={slot}`, z-[70] above the viewer): Take a new photo · Upload a new photo · Remove the photo (only with a photo; the house `ConfirmModal` at `overlayZClass="z-[80]"` naming what is lost). A guardian passes `targetProfileId` (both routes' acting gate).
- **Tap to view:** `ProfileCoverHeader` takes `onCoverTap` / `onAvatarTap` — passed ONLY when a photo is set, on all three routes; `ProfilePhotoViewer.tsx` is the house `MediaLightbox` with one item (the counter shows only for >1) and a `topAction` Edit for the owner that opens the door. **The pulled-up avatar row is `pointer-events-none`** (only the avatar wrapper takes the pointer): it overlaps the cover's lower band and used to catch every tap there — the cover's view button and the owner's Add cover photo control. Never give that row a pointer again.
- **No upload button on the profile (Convention 52, Oct 25 2026 — until then "Add profile picture" / "Add cover photo" showed while a slot was empty):** an empty slot shows the default picture / plain cover, exactly as a visitor sees it; **Edit Profile's Basic tab is where a photo is set** (Change profile picture / Change cover photo, with a preview of the pending pick, uploaded on Save Basic; `basicForm.cover_file` rides beside `avatar_file`). Once set, the photo itself is the door (tap → viewer → Edit → Take / Upload / Adjust / Remove) — an on-demand action on a set photo, not an always-on control.
- **Remove:** `DELETE /api/upload/avatar` and `DELETE /api/upload/cover` (the POSTs' files, so THE write-gate list is unchanged) null the column and remove OUR file only — `src/lib/profiles/photo-paths.ts managedProfilePhotoPath(url, slot)` (pure: the four legacy avatar buckets, `covers/`; a Google or foreign URL → null); the avatar's `/u/` head revalidates. `PUT /api/profile` strips `cover_url` as it does `avatar_url`.
- **Pinned by:** `photo-paths.test.ts`; `e2e/profile-photos.spec.ts` (@mobile — Chromium, WebKit and Android): empty → both buttons; each added through the door → the buttons go; tap → viewer (no counter) → Edit → Remove → confirm → the button and the file; Edit Profile offers both photos.

## The kept original and Adjust (PR 5 — part B, migration 264, the program's last DDL)

Tom: *"Adjust the current photo — re-crop or reposition without re-uploading."* His decision: keep the ORIGINAL photo and its crop, so an adjustment never re-crops a crop.

- **The data (264):** `profiles.avatar_source_url` / `avatar_recipe` and `cover_source_url` / `cover_recipe`, all nullable — the kept original (bounded to 2048 px on the device, in the PRIVATE `uploads` bucket under `profile-sources/{profileId}/{slot}-{ts}.{ext}`) and the editor's recipe envelope that made the render. `avatar_url` / `cover_url` stay THE displayed photos. The four columns are scanned by the storage sweep (`URL_SOURCE_COLUMNS`), collected by the deletion engine, NULLed by the departed-account strip, and stripped from `PUT /api/profile` — the slot's photo route is the ONE writer.
- **The rules** (`src/lib/profiles/photo-recipe.ts`, pure): `parseProfilePhotoRecipe` (the envelope → an IMAGE recipe, or null — the WHOLE editor recipe: crop, adjustments, filter, masks, retouch, text, perspective), `profileSourcePath`, `profileSourceProxyUrl` (the owner-only door, `?v=` busts on the file name), `ProfilePhotoPayload` (`file` the render · `source` the original or null · `recipe` · `sameSource`). `photo-paths.ts managedProfileSourcePath` says which originals are ours.
- **The contract** (both POSTs, `photo-source-server.ts readPhotoPostFields` + `storeProfilePhoto`): the derived file as before, plus `source` (≤10 MB, image), `recipe` (JSON envelope) and `sameSource=1`. A new source → the row names it and its recipe, the previous original is removed; `sameSource` → the recipe alone changes, the original stays (400 when none is stored); neither → both NULL (an old client, onboarding's plain upload — Adjust then starts from the render). The previous render is always removed; a row failure rolls this call's uploads back. `removeProfilePhoto` NULLs the three columns and removes both files. The response carries `{slot}_source_url` + `{slot}_recipe`.
- **The proxy:** `GET /api/media/profile-source/[id]?slot=avatar|cover` — signed-in, the owner or a consented guardian (the acting gate), the profile's OWN source only, only from `uploads/profile-sources/`, `private, no-store`; a stranger gets the same 404 as "no original".
- **On the device** (`photo-upload-client.ts`): `prepareProfileSource` keeps a JPEG / PNG / WebP within 2048 px as is and re-encodes anything else (HEIC, GIF, a 12 MP capture) to a bounded JPEG — null on failure (the render uploads alone); `profilePhotoFormData` is the one body; `assetFromProfilePhoto` opens the original (through the proxy) at its stored crop, or the render with no recipe.
- **The engine:** a camera capture opens the editor exactly like a pick (Tom, Oct 15 2026; it used to attach a centred crop at once — `captureRecipe` / `centeredCrop` are gone). "Adjust the current photo" (`data-photo-adjust`, offered whenever the slot holds a photo) opens the full editor on the kept original with every stored edit; Done sends the new render with `sameSource`. A photo with no original (set before 264) adjusts from the render itself, which becomes the original — lossy once, never a spiral. Deferred mode (Edit Profile) holds the whole payload per slot (`basicForm.avatar_photo` / `cover_photo`) and POSTs it on Save.
- **Pinned by:** `photo-recipe.test.ts`, `photo-paths.test.ts`, the sweep's column + writer registries, the departed-column test (264 is written one `ADD COLUMN` per statement for the live-schema reader), and `e2e/profile-photos.spec.ts` (the originals exist with their crops; Adjust changes the render, keeps the original, writes no second one; Remove takes the original too).

## The sport setup is steps (Convention 51 — Program D, Oct 20 2026, #1246–#1247, zero DDL)

**One Sports tab; a sport's setup is a few short steps derived from its schema; every field optional; one save per sport; the row's summary line is the truth; the sports choice saves from the Sports tab.** Tom (item 4 of the flow changes): "redesign the sport setup into short steps". Until Oct 20 2026 Edit Profile carried ONE TAB PER REGISTERED SPORT (≈ 15 — every sport in the app, most of them not the athlete's), each a two-column form, and the sports picker sat at the bottom of the long Basic tab.

- **The tabs:** Basic · **Sports** · Body Metrics · Socials · Recruiting (`EditProfileTabs.tsx generateTabs`, five fixed ids; `TabId` is that union). The Sports tab holds "Your sports" (`SportMultiSelect`, moved from Basic; the first is the primary) and **a row per sport in the athlete's selection** (`data-sport-row={key}`, `data-sport-row-state="set|empty|none"`): icon, name, `summaryLine` (or "Not set up yet"; "Nothing to set up yet" for a sport with no schema), and **Set up** (empty) / **Edit** → `SportSetupFlow` (`data-sport-setup-open`). A sport just added is saved by **Save Sports** before it can be set up ("Save your sports first").
- **The sports choice saves from the Sports tab:** `saveTab('sports')` owns the added → `PUT /api/sport-settings { settings: {} }`, removed → `DELETE ?sport=` (the "Remove sports?" confirm first), and the primary → `profiles.sport`; **Save Basic never touches sports** (the `sport` key left its payload — the pin "a Basic save keeps the primary" holds for free). A guardian acting for an athlete never sees the Sports tab (`/api/sport-settings` is session-anchored; the old sport-tab rule, now one tab).
- **The steps (`src/lib/sports/settings-steps.ts`, pure):** `stepsForSchema(schema, name)` → "About you in {sport}" (the `preferences` group — a field with no group is a preference — ≤ 5 a step), "Competitive profile" (the `competitive` group minus personal bests), "Personal bests" (the `pb_*` keys, ≤ 8; five events today), "Review" (owns no field). **An empty group yields no step** (swimming, cycling, running, rowing, track & field have no preferences). `stepIndexForKey` sends a validation error back to the step that owns the field. `summaryLine(schema, settings, 3)` is the row's line through `settingsToDisplayItems` — the same labels the profile chips show.
- **The flow (`src/components/SportSetupFlow.tsx`):** `StepFlow` (`src/components/StepFlow.tsx` — "Step n of N · {label}", a dot row with `aria-current="step"`, sticky Back / Next / finish, ≥ 44 px) over the steps; each step renders its keys through **`SportSettingsField`** — the one field renderer (`renderField` extracted from the old one-page form, which is deleted); the Review step lists every field ("Not set" when blank); **Save** is the ONE write: `validateSettingsValues` → `mergeSettingsForSave` → `PUT /api/sport-settings` through the editor's `saveSportSetup`, which then updates the editor's values and that sport's dirty snapshot (`settings:<key>`) so the editor's own `isDirty` stays truthful. The flow edits a copy; **nothing is written before Save**; closing with unsaved answers asks ("Discard your {sport} setup?", `overlayZClass` z-[80] above the flow's z-[70] above the editor's z-50). A full-screen sheet on a phone, a centred panel from `sm`.
- **The doors:** `?edit=sport` opens the editor on the Sports tab (`athlete/page.tsx setEditInitialTab('sports')`); `GetStartedCard` "Set level" is `/athlete?edit=sport`; the pencil and the header menu open it on the last tab used. `ProfileSports` "Add sports" is gone (Convention 52, Oct 25 2026). No per-sport deep link exists (none ever did).
- **Pinned by:** `settings-steps.test.ts`, `step-flow.test.ts`, `sport-setup-ui.test.ts` (five tabs, no per-sport tab, the form deleted, the save path, the flow's hooks), `e2e/edit-profile.spec.ts` (the Sports tab is current after `?edit=sport`; golf through its steps, one save, the row's line, the mid-flow confirm; track & field's three steps with the PBs on step 2), `profile-sports.spec.ts` (Add sports lands on the Sports tab), `get-started-mobile.spec.ts`.

## The profile is a profile, not a settings form (Convention 52 — Oct 25 2026, zero DDL)

Tom: *"The owner's profile page currently shows every editing control at all times: sport selection, social link inputs, bio and detail fields. Because the profile is also where a lot of day-to-day activity happens (posts, media, stats, orgs), that clutter gets in the way of everything else on the page. … The profile is a place the user works from, so it stays clean. Editing is a separate, explicit step the user opens and closes."*

- **The rule:** the owner's `/athlete` renders the SAME read-only view a visitor sees on `/athlete/[id]`, plus ONE control — the Edit profile pencil in the cover's corner (`data-profile-edit`; the header menu's Edit Profile entry opens the same editor). Every profile FIELD — name, handle, bio, the private details, the photos, the sports choice and each sport's setup, height / weight / DOB / location / class year, the four social handles — is edited in **Edit Profile** (`EditProfileTabs`: Basic · Sports · Body Metrics · Socials), never inline on the profile. **Save and Close both return to the profile:** Close through `useDirtyClose` + `ConfirmModal` as before; a tab's Save closes the editor too (the root-mounted editor already did), asking first when ANOTHER tab still holds unsaved typing (the house discard prompt — nothing typed is dropped silently).
- **Gone from `/athlete` (Oct 25 2026):** the four inline social-handle editors (`InlineEdit` and its context — the page's only `autoFocus` sites), the "Add your bio" / "Add your name in Edit Profile" nudges, the achievements' empty label, the owner-only Sport / Team / Position / Class grid (Position and Team were never columns), the empty-slot "Add profile picture" / "Add cover photo" buttons and the page's own `ProfilePhotoDoor` mount; from `ProfileSports` the owner's "No sports yet — Add sports" prompt (empty → nothing, for everyone); from `TrainingHero` the owner's empty height / weight slots ("Add your height." — a slot shows only with a value, for everyone). The page writes no profile field itself (no `PUT /api/profile`).
- **One rendering for the socials:** `src/components/profile/ProfileSocialLinks.tsx` — the outbound links (X · Instagram · TikTok · Facebook, `formatSocialHandle` / `formatSocialHandleDisplay`, the "{name} on {network}" labels), used by BOTH `/athlete` (its own row under the stats, `role="list"` "Social media links") and `/athlete/[id]` (siblings in the stats row); nothing when no handle is set. `/u/` keeps its CDN payload's own rendering.
- **What STAYS owner-only (Tom's decisions, Oct 25 2026 — activity, not editing):** Create Post on My Media; the sport quick links; `OrgMembershipsStrip`; the sport **pins** (Pin / Unpin / Move — arranging one's own view); `FeaturedPosts` unpin; the tabs' Add / Start / Log actions and their owner-addressed empty-state copy (Achievements, Equipment, Training, Tagged, Stats, Badges); the photo viewer's Edit door on a SET photo (Take / Upload / Adjust / Remove); the Training settings gear.
- **Pinned by:** `profile-not-a-form.test.ts` (source: no `InlineEdit`, no `getPlaceholder('ADD_`, no add-photo buttons, bio / achievements gated, `ProfileSocialLinks` on both routes, one `mode="owner"` corner control, Save closes, no `data-sports-empty`, no "Add your height"); `input-zoom-guard.test.ts` (the page left the `autoFocus` list); `sport-setup-ui.test.ts` (the doors); e2e `profile-header-actions` (one `[data-profile-edit]`, no X-handle input, no "Add your bio", no empty-slot buttons, no `input` inside the cover card), `profile-sports` (no sport → no `#sports`; the pencil → Sports tab), `profile-photos` / `photo-open-timing` / `profile-cover-browsers` (the first photo through Edit Profile → Basic → Save Basic; the viewer's door on a set photo), `edit-profile` (Save Basic returns to the profile; unsaved typing on another tab asks first).
