# Videos — the linked full games and their highlights

The record of the program is in `docs/devlog.md` (Nov 4 2026); the phases ahead are in `docs/VIDEOS.md`.

## Convention 57 — A long video is a link, not an upload (Videos program, Nov 4 2026, migration 296)

**Tom's rule:** a full game, a tournament, a broadcast — anything long — lives on YouTube. Edge Athlete links it, places it where it belongs, and marks its highlights. It never downloads, transcodes, re-hosts or edits the video. A short clip stays a post (Convention 43's native path: 3 minutes, 50 MB, `VideoFrame`); the two never merge.

**The model (296).** `videos`: `provider` (`youtube` today; the column is the seam for `native` and `live` later) + `provider_video_id` (the 11-character id — never a URL; every URL is REBUILT from the id), the owner (`profile_id` XOR `org_id`), an optional place (`sport_event_id` XOR `contest_id`), `title`, `description`, `sport_key`, `duration_ms` (null until a later phase reads it), `status` (`published | hidden`), `created_by_user_id` (the guardian or staff member who added it). The same video once per owner (`videos_provider_owner_uidx`). `video_highlights`: `start_ms >= 0`, optional `end_ms > start_ms`, `label`, `meta` (`hole`, `score`, `note` — a closed vocabulary, unknown keys refused), ordered by `start_ms`. Both posture A; the authorization is the pure rule (`src/lib/videos/rules.ts`) through the ONE writer (`src/lib/videos/videos-server.ts`).

**Who sees, who manages.** A hidden video is the owner's "Only me" / the org's "Managers only" — the one per-video switch; who sees a PUBLISHED one is the account's privacy, never a per-video audience (the posting privacy rule): a profile's video follows `canViewProfile` (a stranger: the profile is public and present); an org's follows the org gallery's gate (public org: everyone; private: members); a place's list applies the OWNER's rule row by row (a private profile's video on a public event stays the profile's). Management: the owner or an approved guardian (`resolveActingProfile`, the one acting-as gate); for an org, the `manage_video` intent — the ladder's owner / manager, or the website section's staff grant (`INTENT_SECTION.manage_video = 'website'`; no new section, zero DDL). Attaching to a place needs the place's manager: `readSportEventAccess(...).canManage` for an event, the competition's manager (`requireCompetitionManager`) for a contest — on top of owning the video. A refusal is the 404 of not-found (the contest rule).

**A highlight is a cue, not a clip.** Tapping one starts the player at its second (`?start=` on a REMOUNTED embed — no IFrame Player API script, nothing the static CSP would block); an `end_ms` is a note on the marker, never a cut; the whole video stays watchable, and an unlisted YouTube link is not Edge Athlete access control. The list is in time order — "reorder" is editing the time. No YouTube Data API: the title is typed, the duration unknown until Phase 3.

**The link.** `src/lib/videos/youtube.ts` wraps the site builder's zero-import parser (`parseEmbedUrl` — watch, youtu.be, shorts, live, embed, the mobile host) and adds the `t=` a "share at" link carries; `embedSrcAt` builds the frame from `EMBED_FRAME_HOSTS[0]` (youtube-nocookie.com — the CSP's one host list, pinned equal by `embeds.test.ts`); `thumbUrl` is the i.ytimg.com poster (img-src https:). The player (`src/components/videos/YouTubePlayer.tsx`) is click-to-play (the help centre's rule: a phone never pays for a player it did not ask for), the official responsive embed with its controls and branding untouched, and a line that opens the watch page when the frame cannot play (private, deleted, region-blocked, embedding off — YouTube's own notice sits inside the frame).

**The doors.** The Create menu's fifth door, **Full game** (`ui-conventions.md`, "The Create menu"); the composer's "too long" hint names the same door (the tile's "Too long — trim in the editor" line is unchanged); the profile's Videos tab (both routes; the owner's Add = Convention 52's tab-action exception); the org's Videos bubble (registry priority 95, between Photos and Affiliations, never pinned); the event's Videos tab (before Gallery, which stays last); the contest's Videos section (a client island in the server page, like Posts); the console's contest media panel. `/videos/new` is `StepFlow` over `video-steps.ts` (Link · Details · Where); `/videos/[id]` is a server shell over `VideoScreen`. `/videos` is a reserved root (`RESERVED_ROOT_SLUGS`, seeded into `reserved_handles` by 296).

**The API.** `GET /api/videos?profileId=|side=&orgId=|sportEventId=|contestId=` (anonymous where the context is public; `can_add` for the viewer), `POST /api/videos`, `GET | PATCH | DELETE /api/videos/[id]`, `POST /api/videos/[id]/highlights`, `PATCH | DELETE /api/videos/[id]/highlights/[highlightId]`. Every write spends `video-write` (60 an hour, per account). Every payload `private, no-store`.

**Departure.** `videos.profile_id` is `goes` (a person's own linked games leave with them; `mustDelete('videos', 'profile_id')`); an org's videos stay the org's; `created_by_user_id` is SET NULL.

## Phase 1b — every other upload surface (Nov 5 2026, migration 297)

Tom: "any area where you can upload videos should have the YouTube integration." 297 adds three nullable places to `videos` — `group_post_id` (a golf round), `activity_id`, `workout_session_id` — each ON DELETE SET NULL, the one-place CHECK over the five. **Who may attach** mirrors the place's own write rule, never the video's owner alone (`placeRight` in `videos-server.ts`): a round = its creator or a CONFIRMED participant (the Media tab's rule); an activity = its owner or an approved guardian (`readActivityForViewer(...).audience === 'owner'`); a workout = its owner only. **Who may see a place's list** = the place's own view rule (`canViewSharedRound` over EVERY participant row; `readActivityForViewer`; the `/api/workouts/[id]` non-owner rule — completed, decided, not hidden, the training privacy aspect, public or an accepted follow — answered as the videos' 404), then the owner's rule row by row. The video row's owner is always the actor's own profile for these three doors. One row per owner still holds: linking a video already on the profile to a place is a PATCH of that row; the 409 names the existing one (`existing_id`) and the door offers to open it.

**The surfaces.** The round card's Media tab (`RoundVideos`, above the capture row, on `/live/[groupPostId]` and the feed card alike); the event live page's read-only strip (`EventLiveVideos`, silent at zero — the Videos tab holds the door); the activity screen (`data-activity-videos` after Photos, the owner's "Full recording (YouTube)" beside the capture buttons); the workout review header's "Full session (YouTube)" and the workout card's strip (fetched once expanded, silent at zero). **Messages:** the first YouTube link in a text message renders the click-to-play poster under the bubble (`data-message-youtube`) — a preview at render time, never a row, no DDL; the player seeks on a share link's `t=`. **The public org site:** a `video_list` web tile (a new key — `videos` is the in-app bubble), gated by the GALLERY module (the org gallery's gate, so a private club's tile is members-only by the existing audience rule), over `fetchPublicOrgVideos` — the org's own PUBLISHED rows, never a profile-owned video, never a profile join; rendered server-side as an `<iframe srcdoc>` poster built from the 11-character id (nothing from YouTube loads before the tap; a srcdoc frame is exempt from `frame-src` and the tap's navigation to youtube-nocookie is already admitted — zero CSP change); an org-owned video write purges the org's site tag. The sample canvas draws `SampleFrame` for it (S2: never a third-party request from sample data). `VideosGrid` gained `hideWhenEmpty` / `hideDoor` for the read-only strips.

## Phase 3 — the YouTube connection and direct uploads (Nov 5 2026, migration 298)

**The connection** is per owner (a profile XOR an org; `youtube_connections`, posture A, the one writer `youtube-connections-server.ts`) and is a PERSON's Google grant: `connected_by_user_id`. **Who may connect, disconnect and link** = the owner's video manager (Phase 1's two gates — the person or a guardian; the org's `manage_video`). **Who may upload** = that manager AND the connector, on a standing connection (`uploadRight`): an org's channel is never an app role. **The flow** = `GET /api/videos/youtube/start?owner=&scope=` (a navigation; refusals return to the owner's Videos surface as `youtube_error=<word>`) → Google (Authorization Code + PKCE S256, `access_type=offline`, `prompt=consent`, `include_granted_scopes`) → `GET …/callback` (the signed state for THIS account, owner and scope, ten minutes; the verifier from the `ea-yt-pkce` cookie, cleared either way; the manage and moderation checks again; a refresh token required; the channel of the account that said yes — none → `nochannel`) → the row, sealed with the owner as the box's context. **Scopes are incremental:** `readonly` at connect, `upload` on the first upload (the upload session answers 409 `needs_scope` until then). **The token** (`withAccessToken`): the sealed access token while a minute or more remains, else a refresh sealed again; `invalid_grant` → `revoked` (the card: "reconnect" — also Google's 7-day expiry while the OAuth app is in Testing). **The upload** = the server opens the resumable session (`POST …/upload-session`: title ≤ 100, description ≤ 5000, public | unlisted | private, the size and the type, the Sports category) and answers the session URI + the connector's own hour-long access token; the device PUTs 8 MB chunks with `Content-Range` (`youtube-upload.ts`; a 308 + `Range` resumes; cancel aborts the chunk); the id is then a row through the ordinary `POST /api/videos`. The bytes never pass through Edge Athlete; `connect-src` admits `www.googleapis.com` and nothing else of Google's. **The reads:** `GET …/connection?owner=` (the projection, never the secret; managers only, else 404), `GET …/channel-uploads?owner=` (the uploads playlist = the channel id with UC → UU; newest first, one tap links), `POST /api/videos/[id]/refresh` (the duration from `videos.list` through the owner's connection). **Disconnect** = revoke at Google best effort, then DELETE; the videos stay. **Departure:** both profile keys `goes`. **Offered only when** `YOUTUBE_CLIENT_ID` + `YOUTUBE_CLIENT_SECRET` + `CONNECTIONS_ENC_KEY` are set (unset = no card, 404 on the doors); `YOUTUBE_MOCK_BASE` points the hosts at the e2e stand-in and is ignored in production. **Legal:** the privacy page's Google entry names the channel, the uploads list and the uploads; the terms name YouTube's Terms of Service and Google's Privacy Policy.

**The doors.** The profile's Videos tab (the owner / a guardian) and the org console's website section carry the channel card (Connect · Allow uploads · Reconnect · Disconnect; whose grant it is); `/videos/new`'s Link step, once the default owner is connected, offers "Pick from your channel" (one tap fills the link) and, for the connector, "Upload a file" (the panel: file, title, description, privacy, the progress line, Cancel; done → the Details step); the video page's "Refresh from YouTube".

**Pinned by:** `migration-298.test.ts`, `youtube-connection.test.ts`, `youtube-oauth.test.ts`, the csp and legal pins, the departure classification test; `e2e/youtube-connect.spec.ts` (the profile: connect → the channel list → a one-tap link → refresh fills the duration → 409 needs_scope → the second consent → the session → two resumable PUTs with a 308 between → the row → disconnect, the videos stay; the org: denied, no channel, the owner's grant, a manager links but cannot upload, a stranger is refused).

**Non-goals of this phase (deliberate):** Google OAuth, channel import, uploading to YouTube, downloading / caching / transcoding / re-hosting, browser editing of a full game, live streaming, teaser extraction from a local file — `docs/VIDEOS.md` holds the phases.
