# Videos — the linked full games and their highlights

The record of the program is in `docs/devlog.md` (Nov 4 2026); the phases ahead are in `docs/VIDEOS.md`.

## Convention 57 — A long video is a link, not an upload (Videos program, Nov 4 2026, migration 296)

**Tom's rule:** a full game, a tournament, a broadcast — anything long — lives on YouTube. Edge Athlete links it, places it where it belongs, and marks its highlights. It never downloads, transcodes, re-hosts or edits the video. A short clip stays a post (Convention 43's native path: 3 minutes, 50 MB, `VideoFrame`); the two never merge.

**The model (296).** `videos`: `provider` (`youtube` today; the column is the seam for `native` and `live` later) + `provider_video_id` (the 11-character id — never a URL; every URL is REBUILT from the id), the owner (`profile_id` XOR `org_id`), an optional place (`sport_event_id` XOR `contest_id`), `title`, `description`, `sport_key`, `duration_ms` (null until a later phase reads it), `status` (`published | hidden`), `created_by_user_id` (the guardian or staff member who added it). The same video once per owner (`videos_provider_owner_uidx`). `video_highlights`: `start_ms >= 0`, optional `end_ms > start_ms`, `label`, `meta` (`hole`, `score`, `note` — a closed vocabulary, unknown keys refused), ordered by `start_ms`. Both posture A; the authorization is the pure rule (`src/lib/videos/rules.ts`) through the ONE writer (`src/lib/videos/videos-server.ts`).

**Who sees, who manages.** A hidden video is the owner's "Only me" / the org's "Managers only" — the one per-video switch; who sees a PUBLISHED one is the account's privacy, never a per-video audience (the posting privacy rule): a profile's video follows `canViewProfile` (a stranger: the profile is public and present); an org's follows the org gallery's gate (public org: everyone; private: members); a place's list applies the OWNER's rule row by row (a private profile's video on a public event stays the profile's). Management: the owner or an approved guardian (`resolveActingProfile`, the one acting-as gate); for an org, the `manage_video` intent — the ladder's owner / manager, or the website section's staff grant (`INTENT_SECTION.manage_video = 'website'`; no new section, zero DDL). Attaching to a place needs the place's manager: `readSportEventAccess(...).canManage` for an event, the competition's manager (`requireCompetitionManager`) for a contest — on top of owning the video. A refusal is the 404 of not-found (the contest rule).

**A highlight is a cue, not a clip.** Tapping one starts the player at its second (`?start=` on a REMOUNTED embed — no IFrame Player API script, nothing the static CSP would block); an `end_ms` is a note on the marker, never a cut; the whole video stays watchable, and an unlisted YouTube link is not Edge Athlete access control. The list is in time order — "reorder" is editing the time. No YouTube Data API: the title is typed, the duration unknown until Phase 3.

**The link.** `src/lib/videos/youtube.ts` wraps the site builder's zero-import parser (`parseEmbedUrl` — watch, youtu.be, shorts, live, embed, the mobile host) and adds the `t=` a "share at" link carries; `embedSrcAt` builds the frame from `EMBED_FRAME_HOSTS[0]` (youtube-nocookie.com — the CSP's one host list, pinned equal by `embeds.test.ts`); `thumbUrl` is the i.ytimg.com poster (img-src https:). The player (`src/components/videos/YouTubePlayer.tsx`) is click-to-play (the help centre's rule: a phone never pays for a player it did not ask for), the official responsive embed with its controls and branding untouched, and a line that opens the watch page when the frame cannot play (private, deleted, region-blocked, embedding off — YouTube's own notice sits inside the frame).

**The doors.** The Create menu's fifth door, **Full game** (`ui-conventions.md`, "The Create menu"); the composer's "too long" hint names the same door (the tile's "Too long — trim in the editor" line is unchanged); the profile's Videos tab (both routes; the owner's Add = Convention 52's tab-action exception); the org's Videos bubble (registry priority 95, between Photos and Affiliations, never pinned); the event's Videos tab (before Gallery, which stays last); the contest's Videos section (a client island in the server page, like Posts); the console's contest media panel. `/videos/new` is `StepFlow` over `video-steps.ts` (Link · Details · Where); `/videos/[id]` is a server shell over `VideoScreen`. `/videos` is a reserved root (`RESERVED_ROOT_SLUGS`, seeded into `reserved_handles` by 296).

**The API.** `GET /api/videos?profileId=|side=&orgId=|sportEventId=|contestId=` (anonymous where the context is public; `can_add` for the viewer), `POST /api/videos`, `GET | PATCH | DELETE /api/videos/[id]`, `POST /api/videos/[id]/highlights`, `PATCH | DELETE /api/videos/[id]/highlights/[highlightId]`. Every write spends `video-write` (60 an hour, per account). Every payload `private, no-store`.

**Departure.** `videos.profile_id` is `goes` (a person's own linked games leave with them; `mustDelete('videos', 'profile_id')`); an org's videos stay the org's; `created_by_user_id` is SET NULL.

**Pinned by:** `src/lib/videos/__tests__/{youtube,rules,migration-296}.test.ts`, `src/lib/__tests__/videos-ui.test.ts`, the tab pins in `page-rules`, `media`, `team-engine`, `app-layout`, `app-composition`; `e2e/videos.spec.ts`, `e2e/videos-mobile.spec.ts`, `e2e/org-app-videos.spec.ts`, `e2e/header-create.spec.ts` (five doors).

**Paste and go (Nov 6 2026, zero DDL).** A pasted link reads itself from YouTube once (`GET /api/videos/youtube/lookup?id=&owner=`: signed in, the `video-lookup` bucket, the owner's connection first — a private video of their own — else the server-only key; neither → `available: false` and the flow behaves as before): the title fills an EMPTY title field (editable), the duration and the live state show under the poster, a **private** video is refused before Save (the step rule's `blocked` sentence — it would play for nobody), **embedding off** is allowed with the sentence and the video page shows the watch door in place of the frame (`data-video-no-embed`; the page asks the lookup once, silently). **Chapters** in the description follow YouTube's own rule (`parseChapters`: a timestamp at a line start, the first at 0:00, ascending, at least three, ten seconds apart) and become the first highlights in ONE write — `POST /api/videos/[id]/highlights/import` (a manager, `video-write` once, ≤ 100 rows, each through the one highlight rule, refused 409 when the list is not empty); a chapter runs to the next one, the last to the end (`chaptersToHighlights`). The card shows the duration badge. Pinned by `youtube-connection.test.ts` (the chapter rule's five conditions, the open last chapter, the refusal words), the `videos-ui.test` paste-and-go block, `e2e/videos-lookup.spec.ts`.

**The player that knows the time (Nov 6 2026, zero DDL, zero CSP).** The player is YouTube's frame — with YouTube's IFrame Player API when it answers, the plain frame otherwise. The API script is loaded once per page, after the poster tap, by TRUSTED code (`youtube-player-api.ts`: `document.createElement('script')` appended to the head — the CSP's `'strict-dynamic'` trusts it and what it loads in turn; nothing is parser-inserted, no host is added to the policy), with `PLAYER_READY_TIMEOUT_MS` (4 s) to announce itself; the frame's host stays youtube-nocookie.com (`PLAYER_HOST`). In API mode the page knows the playhead (`PLAYER_TICK_MS` while playing) and a highlight tap SEEKS instead of remounting; in frame mode everything is as before (`data-video-player-mode`). What the API unlocks is pure rules in `player-rules.ts`: **"This moment"** (`markMomentMs`: the playhead typed into the time field for a VOD; the live "Now" keeps the server's stamp), **"Play highlights"** (`playlistOf`: the markers in time order, an open marker plays `OPEN_HIGHLIGHT_MS` = 20 s; `nextInPlaylist`: stay / next / done; `activeHighlightAt`: the active row follows the playhead; a row tap leaves the walk), **resume** (`localStorage` per video id, fail-open, saved every `RESUME_SAVE_EVERY_MS`, cleared at the end; `resumeOffer`: nothing under `RESUME_MIN_MS` = 30 s nor within the last 30 s; a chip over the poster, never automatic). Off the video page nothing loads the API — the feed card and the message poster stay poster-first, plain frame on tap. Pinned by `player-rules.test.ts`, the `videos-ui.test` player block (createElement never innerHTML, the frame fallback, the mark path, no CSP change, nothing off the page), `e2e/videos-player.spec.ts`.

## Phase 1b — every other upload surface (Nov 5 2026, migration 297)

Tom: "any area where you can upload videos should have the YouTube integration." 297 adds three nullable places to `videos` — `group_post_id` (a golf round), `activity_id`, `workout_session_id` — each ON DELETE SET NULL, the one-place CHECK over the five. **Who may attach** mirrors the place's own write rule, never the video's owner alone (`placeRight` in `videos-server.ts`): a round = its creator or a CONFIRMED participant (the Media tab's rule); an activity = its owner or an approved guardian (`readActivityForViewer(...).audience === 'owner'`); a workout = its owner only. **Who may see a place's list** = the place's own view rule (`canViewSharedRound` over EVERY participant row; `readActivityForViewer`; the `/api/workouts/[id]` non-owner rule — completed, decided, not hidden, the training privacy aspect, public or an accepted follow — answered as the videos' 404), then the owner's rule row by row. The video row's owner is always the actor's own profile for these three doors. One row per owner still holds: linking a video already on the profile to a place is a PATCH of that row; the 409 names the existing one (`existing_id`) and the door offers to open it.

**The surfaces.** The round card's Media tab (`RoundVideos`, above the capture row, on `/live/[groupPostId]` and the feed card alike); the event live page's read-only strip (`EventLiveVideos`, silent at zero — the Videos tab holds the door); the activity screen (`data-activity-videos` after Photos, the owner's "Full recording (YouTube)" beside the capture buttons); the workout review header's "Full session (YouTube)" and the workout card's strip (fetched once expanded, silent at zero). **Messages:** the first YouTube link in a text message renders the click-to-play poster under the bubble (`data-message-youtube`) — a preview at render time, never a row, no DDL; the player seeks on a share link's `t=`. **The public org site:** a `video_list` web tile (a new key — `videos` is the in-app bubble), gated by the GALLERY module (the org gallery's gate, so a private club's tile is members-only by the existing audience rule), over `fetchPublicOrgVideos` — the org's own PUBLISHED rows, never a profile-owned video, never a profile join; rendered server-side as an `<iframe srcdoc>` poster built from the 11-character id (nothing from YouTube loads before the tap; a srcdoc frame is exempt from `frame-src` and the tap's navigation to youtube-nocookie is already admitted — zero CSP change); an org-owned video write purges the org's site tag. The sample canvas draws `SampleFrame` for it (S2: never a third-party request from sample data). `VideosGrid` gained `hideWhenEmpty` / `hideDoor` for the read-only strips.

## Phase 3 — the YouTube connection and direct uploads (Nov 5 2026, migration 298)

**The connection** is per owner (a profile XOR an org; `youtube_connections`, posture A, the one writer `youtube-connections-server.ts`) and is a PERSON's Google grant: `connected_by_user_id`. **Who may connect, disconnect and link** = the owner's video manager (Phase 1's two gates — the person or a guardian; the org's `manage_video`). **Who may upload** = that manager AND the connector, on a standing connection (`uploadRight`): an org's channel is never an app role. **The flow** = `GET /api/videos/youtube/start?owner=&scope=` (a navigation; refusals return to the owner's Videos surface as `youtube_error=<word>`) → Google (Authorization Code + PKCE S256, `access_type=offline`, `prompt=consent`, `include_granted_scopes`) → `GET …/callback` (the signed state for THIS account, owner and scope, ten minutes; the verifier from the `ea-yt-pkce` cookie, cleared either way; the manage and moderation checks again; a refresh token required; the channel of the account that said yes — none → `nochannel`) → the row, sealed with the owner as the box's context. **Scopes are incremental:** `readonly` at connect, `upload` on the first upload (the upload session answers 409 `needs_scope` until then). **The token** (`withAccessToken`): the sealed access token while a minute or more remains, else a refresh sealed again; `invalid_grant` → `revoked` (the card: "reconnect" — also Google's 7-day expiry while the OAuth app is in Testing). **The upload** = the server opens the resumable session (`POST …/upload-session`: title ≤ 100, description ≤ 5000, public | unlisted | private, the size and the type, the Sports category) and answers the session URI + the connector's own hour-long access token; the device PUTs 8 MB chunks with `Content-Range` (`youtube-upload.ts`; a 308 + `Range` resumes; cancel aborts the chunk); the id is then a row through the ordinary `POST /api/videos`. The bytes never pass through Edge Athlete; `connect-src` admits `www.googleapis.com` and nothing else of Google's. **The reads:** `GET …/connection?owner=` (the projection, never the secret; managers only, else 404), `GET …/channel-uploads?owner=` (the uploads playlist = the channel id with UC → UU; newest first, one tap links), `POST /api/videos/[id]/refresh` (the duration from `videos.list` through the owner's connection). **Disconnect** = revoke at Google best effort, then DELETE; the videos stay. **Departure:** both profile keys `goes`. **Offered only when** `YOUTUBE_CLIENT_ID` + `YOUTUBE_CLIENT_SECRET` + `CONNECTIONS_ENC_KEY` are set (unset = no card, 404 on the doors); `YOUTUBE_MOCK_BASE` points the hosts at the e2e stand-in and is ignored in production. **Legal:** the privacy page's Google entry names the channel, the uploads list and the uploads; the terms name YouTube's Terms of Service and Google's Privacy Policy.

**The doors.** The profile's Videos tab (the owner / a guardian) and the org console's website section carry the channel card (Connect · Allow uploads · Reconnect · Disconnect; whose grant it is); `/videos/new`'s Link step, once the default owner is connected, offers "Pick from your channel" (one tap fills the link) and, for the connector, "Upload a file" (the panel: file, title, description, privacy, the progress line, Cancel; done → the Details step); the video page's "Refresh from YouTube".

**Pinned by:** `migration-298.test.ts`, `youtube-connection.test.ts`, `youtube-oauth.test.ts`, the csp and legal pins, the departure classification test; `e2e/youtube-connect.spec.ts` (the profile: connect → the channel list → a one-tap link → refresh fills the duration → 409 needs_scope → the second consent → the session → two resumable PUTs with a 308 between → the row → disconnect, the videos stay; the org: denied, no channel, the owner's grant, a manager links but cannot upload, a stranger is refused).

**Self-healing (Nov 10 2026, zero DDL).** A 401 from YouTube is a stale token first, a dead connection last. EVERY call made with an owner's connection goes through `callWithToken` (`youtube-connections-server.ts`) over the pure `withOneRetry`: a token, the call; on a 401 ONE forced refresh and the call once more — never a third. Exactly two things write `revoked`: Google's `invalid_grant` on a refresh, and a 401 on a token minted a moment ago. A transport failure, a 5xx, a quota answer write nothing. Nothing writes `error` any more; a row an older build left there still opens (`tokenFailureFor`) and the next good call makes it `active`. `canUpload` / `canBroadcast` refuse only `revoked`. **The answers say what is true** (`TOKEN_FAILURES`): no row is a 404 "No YouTube channel is connected"; revoked, or a sealed box this deployment cannot read, is a 409 with `reconnect: true`; no answer is a 503. A refusal that is not about the connection has its own words (`CALL_REFUSALS` by `callRefusalWord`: YouTube's daily limit → 429 "try again tomorrow", the channel's upload limit, a plain 403, no answer). **A screen told `reconnect` shows the one door** (`YouTubeReconnectLink` — the start route with the scope that screen needs; the card and the flow ask `reconnectScope`, the widest the connection had): the channel picker (else "Try again"), the upload panel, the broadcast panel; the Full game flow names a connection's problem with that door and hides the picker of a revoked one — never doors that silently vanish. **The health check:** `GET /api/videos/youtube/connection?owner=…&check=1` runs one `channels.list mine` (a unit of quota, the `video-lookup` bucket) through the retry before answering, so a grant that ended reads `revoked` on the card now, not at the next upload, and a renamed channel gets its title; the card asks once per mount, at most every ten minutes per owner on the device (`healthCheckDue`, sessionStorage). Pinned by the `self-healing` blocks of `youtube-connection.test.ts` (the retry's five cases, the failure vocabulary, the refusal words, the writer's source pin: every route calls `callWithToken`, two `markRevoked` sites, no `error` write) and `videos-ui.test.ts`, and `e2e/youtube-connect.spec.ts`'s third test against the stand-in Google (`expireAccess`, `refuseAll`).

## Phase 4a — a linked broadcast the app knows is live (Nov 5 2026, migration 299; the design is `docs/VIDEOS_LIVE.md`)

**The fact.** A YouTube broadcast is a video with the SAME id before, during and after the stream, so a linked broadcast is the `videos` row that already exists; the archive never "becomes" a row. **The model (299):** `live_status none | upcoming | live | ended` (a named CHECK), `scheduled_start_at`, `live_started_at` (YouTube's actual start — the zero of a marker made live), `live_ended_at`, `live_checked_at`; one partial index over what is or will be live. **The one writer** is `src/lib/videos/videos-live-server.ts`; the pure rules are `live-rules.ts` (zero imports).

**Reader-driven, never a clock.** A state is read from YouTube when someone is about to look at a row whose TTL has passed — live 45 s; upcoming within the hour 60 s, further out 10 min; a plain video or an archive never — and the read is CLAIMED by a conditional UPDATE on `live_checked_at` (zero rows = another request is reading), so many viewers cost one Data API unit. The owner's connection reads first (a private broadcast), else the server-only `YOUTUBE_API_KEY`; neither → nothing happens. A `quotaExceeded` answer parks the row ten minutes (the claim dated forward) and the last truth stays on screen. The first read happens on the link (`force`), so an upcoming broadcast shows its time at once and a plain video gets its duration. **What a read's duration does:** nothing while upcoming or live (YouTube says PT0S), fills a null, and replaces the placeholder the moment a broadcast becomes the archive (`durationToRecord`). The three routes call the writer after a list, a read or the first link and re-read when something changed; the writer never imports `videos-server.ts`.

**The surfaces.** The card's LIVE pill or its "Live today at 2:00 PM" line come from the ROW (a card never asks YouTube); the page's state line (streaming now / scheduled / the recording) and its own minute re-read while live or about to be (`liveRefetchMs`); the highlight form's "Now" button — the time is the SERVER's clock against YouTube's actual start (`meta.live = true`), a device's own number is ignored, and it is refused (409) once the stream is over; the markers still seek the recording. **Live Now** (PR B): `GET /api/videos/live-now` — published rows streaming now under the OWNER's own rule row by row (a profile's privacy, a follow counts; an org's reach), signed out included, newest start first, at most ten, refreshed when due before answering; the strip renders the broadcast cards first. Every list puts a live broadcast first, then an upcoming one (`sortLiveFirst`, stable). The public site's tile shows the pill from the org's own row, server-side; a state change on an org's broadcast purges its pages. The header's Live dot does NOT count broadcasts yet — `me_pulse` (292) is SQL; that is migration 300 and the parity spec, its own PR.

**Pinned by:** `migration-299.test.ts`, `live-rules.test.ts` (YouTube's words → ours, the TTLs, "due", the marker's offset, the duration rule, the order, the badge, the poll, the time in words), the `rules.test` meta.live case, the `videos-ui.test` live blocks (the card and page read the row, the "Now" path, the routes call the writer, the writer stays acyclic and claims its read, the key is server-only, the strip's third fetch, the order, the tile); `e2e/videos-live.spec.ts` (upcoming on the link → the card's line → inside the TTL no read → stale → live → the pill, "Now" ≈ 90 s in, the device's time ignored, Live Now for the owner and not a stranger, the `/live` card → ended: the real duration, the marker seeks the recording, "Now" refused, off Live Now → an archive never asked again → the quota keeps the last truth and parks the row).

## Phase 4b — the broadcast created from Edge Athlete (Nov 5 2026, zero DDL)

**The door** is `/videos/new`'s Link step — "Schedule a live broadcast on <channel>" — beside "Pick from your channel" and "Upload a file", so the owner picker, the place prefill and the Details step are reused; it shows for the CONNECTOR only (`canBroadcast` = `canUpload`'s three facts: manages, is the connector, the connection stands). **The right** is `broadcastRight` = `uploadRight` (one function, two names): an org's channel is never an app role. **The scope** is the third incremental one, `live` = `youtube.force-ssl` (sensitive — Google's verification before the public switch; the OAuth app's test users meanwhile), asked at the moment of need: the route answers 409 `{ needs_scope: 'live' }` and the flow's line sends them through `/start?scope=live` once. **The route** `POST /api/videos/youtube/broadcast` (`requireActiveWriter`, the video-write bucket; `parseBroadcastBody`: a title within YouTube's 100, a start at least a minute ahead and within a year, a privacy): `liveBroadcasts.insert` (auto start/stop, the monitor stream off — YouTube itself moves it live when bytes arrive, so 4a's refresh sees it), one new `liveStreams.insert` per broadcast, `liveBroadcasts.bind`; a failure after the broadcast exists deletes it (no orphan). **The key is shown ONCE and never stored or logged:** the answer carries `stream_key`, the RTMP(S) addresses, `studio_url`; the panel shows the key with Copy and two doors (YouTube Studio; an encoder — the address revealed on tap) and the two sentences (the key lives in Studio afterwards; the YouTube phone app wants 50 subscribers, a computer or an encoder none); Continue hands the id to the flow — the row is an ordinary link and 4a's first read makes it `upcoming` with the time. **Eligibility in words** (`BROADCAST_ERRORS`): `not_enabled` (liveStreamingNotEnabled), `blocked` (livePermissionBlocked / insufficientLivePermissions), `refused`, `failed` — 403 + `reason`; never a stack trace. The privacy page says the key is shown once and never stored.

**Pinned by:** `youtube-connection.test.ts` (the third scope, `parseBroadcastBody`'s bounds, the words, Studio's URL, the default start, `canBroadcast`), the `videos-ui.test` 4b block (the door is the connector's, the panel never stores or logs, the route's gates and the orphan delete, the privacy sentence, no new host); `e2e/youtube-broadcast.spec.ts` (connect → 409 needs_scope live → the consent → `scopes` readonly + live → a bad body 400 → not_enabled / blocked in words with nothing created → the manager who did not connect 403 → from the page: the door, the panel, the key sheet with the key, the RTMPS address and the Studio link, the stand-in's broadcast bound to its stream → Continue → Details → Save → the row `upcoming` with the time, the key in no answer and not in the row → the stand-in goes live, the stale row reads it).

**Non-goals of live (deliberate):** a dedicated provider, browser capture, chat, DVR controls, polling by cron, storing a key.

**Non-goals of this phase (deliberate):** Google OAuth, channel import, uploading to YouTube, downloading / caching / transcoding / re-hosting, browser editing of a full game, live streaming, teaser extraction from a local file — `docs/VIDEOS.md` holds the phases.
