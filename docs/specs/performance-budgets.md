# Performance budgets — what every deploy must stay under, and how it is measured

The rules of the performance program (Nov 7 2026). The record of each round lives in `docs/devlog.md`; the numbers in `docs/load/<date>/`; the ranked scale holes in `docs/SCALE_AUDIT.md`.

## Convention 59 — Weight is gated, never guessed

**Why.** On Nov 7 2026 the function that served `/api/posts` traced ~170 MB — the ffmpeg binary, sharp and 95 MB of snapshot photos — because a route that only ENQUEUED a media job imported the worker, and a `readFile` of a computed `.png` path made the tracer include every PNG in the repo. Its first request after a deploy took 1.5–1.8 s against 150 ms warm; a feed open fans out a dozen such calls. Nothing measured it, so nothing noticed for weeks. The same was true of the client: ~185 KB gzipped on every page, the athlete page 627 KB, and no line in the gate would have flagged the next 50 KB.

**The rules.**

1. **Functions.** `scripts/check-function-weight.mjs` (part of `npm run check:weight`, inside `npm run verify` and CI after the build) sums every route's traced bytes (`.next/server/app/**/*.nft.json`) and fails when a route exceeds **25 MB** unless it is on the exempt list in `scripts/function-weight-rules.mjs` with a reason. Today's exemptions: the two media-worker routes (ffmpeg) and the two org card renderers (sharp). Raising the budget or adding an exemption is a decision written in the PR body and the devlog.
2. **The worker boundary.** `src/lib/media/process-server.ts` (ffmpeg, sharp, the temp directory) is imported by `/api/cron/media-jobs` and `/api/admin/media-jobs` ONLY. Every writer enqueues through `src/lib/media/enqueue-server.ts`, which touches no disk, binary or image library. `src/lib/__tests__/media-worker-boundary.test.ts` pins both.
3. **What the tracer may not follow.** `next.config.ts` `outputFileTracingExcludes` keeps `database/**`, `docs/**`, `e2e/**`, `public/**`, `scripts/**`, ffmpeg-static, sharp and `@img/**` out of every function; `outputFileTracingIncludes` puts the binary back into the two worker routes and sharp into the worker and the two card renderers. The include keys are picomatch globs against the normalized app path, so a dynamic segment is written `\\[slug\\]`. `.vercelignore` keeps the snapshots, provenance, docs and workflows off the upload altogether (not `e2e/`: the build's type check reads its helpers through the tests and `playwright.config.ts`). The Sep 30 snapshots are no longer tracked in git (they stay on Tom's Mac and in staging — `docs/RUNBOOK_BACKUP.md`).
4. **Client bundle.** `scripts/check-bundle-weight.mjs` gzips every chunk and fails when the code every page loads (`build-manifest.json` `rootMainFiles`) exceeds **200 KB gz** or any route's first-paint chunks (the `entryJSFiles` of its layout → page tree in its client-reference manifest, root included) exceed **640 KB gz**. Both start where the app was on Nov 7 2026 and RATCHET DOWN as Phase 3 lands (targets: root ≤ 140 KB, route ≤ 350 KB). A new runtime dependency names its gzipped cost and the route that carries it in the PR body, and loads behind `dynamic()` unless it is on the open path.
5. **The cold start is a number.** `scripts/cold-probe.mjs` fires the feed's open path (the document and the dozen API calls, in parallel as a real open does) as a disposable QA user, then four warm runs each, and writes `docs/load/<date>/cold-<label>.md`. Run it before and after any change that touches a function's weight; against production with `TARGET_ENV=prod E2E_ALLOW_PROD=1` (the e2e suite's own guard), one probe at a time.

6. **A deploy is warmed, not discovered.** `.github/workflows/warm.yml` runs on Vercel's `deployment_status` for the Production environment and `scripts/warm.mjs` waits for `/api/health` to carry the deployed sha, then fires the open path (the document and every API call a feed open makes) once in parallel and once more in sequence — no session, a 401 loads the function too. With Fluid Compute the first real open after a merge finds warm functions. `/api/health` answers `boot_ms` (the instance's age) and `requests_served`, so a cold start is a number the probe prints, not a feeling.
7. **The installed app keeps what it already has.** The service worker's activate CARRIES the previous build's `/_next/static/*` entries into the new build's cache before deleting the old one (the same hashed URL is the same bytes); only what the new build never asks for ages out through the entry cap. Pinned by `src/lib/sw/__tests__/static-cache.test.ts`.
8. **The published org sites are built with the deploy.** The `(public)` layouts' `generateStaticParams` return up to 20 published subdomains (`getCachedSitemapSites`; a build without the database returns none), so their first visitor after a deploy gets the CDN's copy; the pages' own `generateStaticParams` keep returning `[]` and every other slug renders on demand as before.
9. **The middleware skips what needs no session:** `manifest.webmanifest` and the font files join the matcher's exclusions.

10. **Nothing heavy runs at boot.** The Sentry server SDK (~420 ms of module evaluation on an M-series Mac, most of a second on Vercel) is imported and initialised on the FIRST ERROR by `src/lib/observability/sentry-server.ts`, never at boot: `instrumentation.ts` imports nothing, the eager `sentry.server.config.ts` / `sentry.edge.config.ts` are gone, and every server module reports through the lazy module's `captureException` / `captureMessage` / `addBreadcrumb`. What is given up is server-side performance traces and automatic breadcrumbs, which the project sampled at 10 % and never read; every error still arrives. `src/lib/__tests__/sentry-server-lazy.test.ts` pins that no server module imports `@sentry/nextjs` statically. The same question — "what does this module cost at boot?" — is asked of every new server dependency; `node -e "const t=process.hrtime.bigint(); require('<pkg>'); console.log(Number((process.hrtime.bigint()-t)/1000000n))"` answers it in a second.

11. **The open path reads through ONE client cache and makes as few calls as it can.** `src/lib/net/query-cache.ts` (rules in `query-cache-rules.ts`): keyed by URL, stale-while-revalidate, in-flight dedupe, prefix invalidation by the writer, a reset on sign-out. The Live Now strip is one read of `GET /api/live-now`, which composes the three live-now handlers in-process and adds no rule; the header's routines are read once and kept five minutes (every routine writer invalidates); the feed's first page (30 s) and a profile's three reads (60 s) paint from the cache on a return; the feed calendar never waits on the household roster. `e2e/perf-feed.spec.ts` holds the budget — `OPEN_PATH_API_BUDGET` API calls on a cold `/feed`, ratcheting down — and `src/lib/__tests__/open-path-cache.test.ts` pins each adoption. A new read on the open path goes through the cache or says in the PR why it cannot. A LIST that renders a control with its own read carries what the control needs (the suggestions carry each person's follow stats; `FollowButton` starts from `initialStats`); a module that wants a number the pulse already holds asks the store, never the network (`MessagesProvider` reuses a pulse younger than 30 s); the browser sends nothing to Sentry without an error (`browserBeaconIntegrations`, `tracesSampleRate` 0, no client reports). Why fewer calls matter beyond latency: on Fluid Compute a burst of simultaneous first requests spawns parallel cold instances (`docs/load/2026-11-07/cold-after-warm.md`) — every call saved is a cold start a phone may not pay.

12. **The installed app reopens to what it had.** `src/lib/net/device-store.ts` (rules in `hydration-rules.ts`) keeps three things in `localStorage` under `ea:hyd:v1:<userId>:<kind>` — the profile (7 days), the pulse's numbers (24 h), the feed's first page on the default scope (24 h, 20 posts) — and paints them before the network answers: `AuthProvider` sets the remembered profile and drops `loading` before its read, `PulseHost` hydrates the badges (the mount read still fetches — `fetchedAt` is never restored), the feed shows the remembered page with the spinner off while it revalidates. The account id is in every key, a copy that is not this account's or is past its lifetime is ignored, and every sign-out path (the explicit one and both dead-session branches) calls `clearDevice()`. Nothing else may store user data on the device (`hydration-adoption.test.ts`); `e2e/hydration.spec.ts` proves the paint with the network held back. Tom's decision, Nov 7 2026.

13. **Every deploy is measured by real browsers.** `page_timings` (305) keeps one row per browser timing metric per page view — the BUILD, the route with ids masked, the metric, the value, the device class from the viewport — and nothing about a person. The beacon (`components/observability/PageTimingBeacon.tsx`) is mounted once in the app layout and sends one batch per page view; the writer is `POST /api/page-timings` behind the `page-timings` IP bucket, 204 whatever happens; the console's Page timings card reads p75 per build per device for the last ten builds; the daily cron keeps 30 days. After every production merge the new build's phone p75 LCP is read on the card and written into the round's devlog entry. Speed Insights stays off (Tom, Nov 7 2026).

14. **Nothing heavy runs on page load either.** The browser Sentry SDK (~60 KB gzipped in the chunks every page loaded) is imported and initialised on the FIRST error (`src/lib/observability/sentry-browser.ts`): `instrumentation-client.ts` installs two buffering handlers and nothing else; the error boundaries and the explicit callers use the lazy module's calls. `sentry-lazy.test.ts` pins both sides. The same question — "what does this run on every page load?" — is asked of every new client dependency before it joins the root; the gate's attribution (`check-bundle-weight`'s largest-chunks list, a marker scan when a name is needed) answers it.

15. **Icons are symbols on one cached sprite, never a webfont.** Font Awesome's stylesheet (90 KB, 23 KB gz on every page) and its three font files (259 KB) are gone. Every icon the app draws is a `<symbol>` in ONE content-hashed sprite (`public/icons/fa-<hash>.svg`, 116 KB / 35 KB gz, cached a day with a week's grace) generated from the package's own SVGs by `scripts/gen-fa-icons.mjs` (the package a build-time dependency; CC BY 4.0 in the sprite and every module header), and drawn by `<FaIcon icon={faX}>` through `<use>` — identical shapes, one request, no FOIT. A glyph module (`src/lib/icons/fa/<name>.ts`) holds only the symbol id and its box, so a route's JavaScript carries ~60 bytes per icon it imports (+8–11 KB gz per route for the whole set of modules and the component, against the 23 KB gz of stylesheet every page lost). Data modules every page imports (the sport registry, the activity catalog, the notification registry, the connections, the privacy options) hold NAMES; the render side maps them (`sport-icons.ts`, `activity-icons.ts`, `notification-icons.ts`). The first cut put the paths in the modules and every route grew ~40 KB gz — the sprite is the lesson. `fa-icons.test.ts` pins that no `<i class="fa …">` remains, that every glyph import has its module and every module its symbol, and that the generator is current.

**Every PR answers three lines** in its description: bytes added to the root bundle (from the gate), API calls added to an open path, database trips added (from the trips pins). Zero is the normal answer.
